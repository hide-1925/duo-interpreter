# Duo Interpreter 拡張 v1.4.32

HTML 本体 **v1.49.21**（ビルド `20260925-v14921-prosody-google-tts`）と対です。

## 1. Realtime の `Pitch=未検出` を直しました

v1.49.19 の `gpt-live-transcribe` 記録で、判断層が決めた6件はすべて**音響なし**で出ていました。
原因は2つ重なっていました。

**（a）判断層が共有マイクの解析器しか見ていなかった。** 解析器は3系統あります ――
共有マイク（`startVU`）、録音分割RESTの `StreamEngine`、Realtime系のエンジン。
判断層は `micProsody`（共有マイク）だけを読んでいたので、**マイクを使わない経路
（タブ音声・VB-CABLE・画面共有）では音響がいつも空**でした。演説を訳す使い方は
まさにこれです。

**（b）`gpt-live-transcribe` のエンジンには解析器が無かった。** 発話境界の判定用に
512点の解析ノードは持っていましたが、`ProsodyAnalyzer` は作っていませんでした。
しかも512点では YIN の探索下限が48kHzで**約189Hz**になり、男性の話声（85〜180Hz）が
丸ごと範囲外に落ちます。ピッチが出るはずがありませんでした。

### 直したこと

- **読む解析器を席で決めるようにしました**（`prosodyAnalyzerFor`）。席が一致する
  エンジン → 席を持たないエンジン（AUTO判定） → 共有マイク、の順に探します。
  字幕カードの音響表示も同じ経路になったので、**タブ音声でもカードに音響が出ます**。
- **`gpt-live-transcribe` に解析専用の2048点ノードを足しました。** 境界判定の512点は
  そのままで、同じ入力から別のノードを取ります。境界判定のRMS窓は変えていません。
- 診断に **`解析器`** を出すようにしました。`Pitch=未検出` の原因が「解析器が無い」のか
  「解析器はあるが検出できていない」のかを切り分けるためです。

```
Prosody取得状態 | Pitch=可 / Energy=可 / Timing=可 / 解析器 live:audio
```

`解析器 無し` と出たら、そのときは音響なしで判断しています。

## 2. Google Cloud Text-to-Speech を追加しました

⚙ → 音声 → 読み上げ → **Google Cloud TTS（Chirp 3: HD / Gemini-TTS）**

**拡張機能も中継サーバーも要りません。** `texttospeech.googleapis.com` は
`Access-Control-Allow-Origin` を要求元へ返し、`x-goog-api-key` を許可ヘッダに
挙げています（実測。`file://` の `Origin: null` でも通ります）。判断層で使っている
`api.typesafe.ai` とは違い、**ページから直接呼べます。**

### 声の系統は3つから選びます

|系統|声の名前|話し方の指示|向き|
|---|---|---|---|
|**Chirp 3: HD**（既定）|`ja-JP-Chirp3-HD-Aoede` のように**自動で組み立て**|なし|低遅延。同時通訳向き|
|**Gemini-TTS**|`Kore` のように素の名前|**文章で指示できる**|表現重視。1発話の待ちは伸びる|
|名前を直接指定|入力した名前そのまま|なし|Neural2 / Studio / WaveNet など従来の声|

**Chirp 3: HD は言語ごとに同じ名前の声がある**ので、名前を選んでおけば
**どの言語でも同じ声で読みます**。A席とB席で別の名前にすれば、どちらの発言か耳で分かります。

Gemini-TTS のモデルは `gemini-2.5-flash-tts`（既定）・`gemini-3.1-flash-tts-preview`・
`gemini-2.5-pro-tts`・`gemini-2.5-flash-lite-preview-tts` から選べます。

### 話速の扱いには実装上の制約があります

**Chirp 3: HD と Gemini-TTS は API 側の話速（`speakingRate`）とピッチに対応していません。**
Chirp 3: HD は既定値を送っても 400 が返ります。そこで、

- この2系統では話速を**ピッチ保持再生**で、音量を Web Audio で出します。
- 「名前を直接指定」で Neural2 などを選んだときだけ、話速を API の `speakingRate`
  （0.25〜2.0倍）へ渡し、足りない分だけ再生側で補います。
- それでも 400 が返った場合は、**指定を外して一度だけ読み直します**。以後その声には
  送りません（`google-retry` としてログに残ります）。読み上げが1つ黙ると、
  聞き手には理由が分かりません。

「実効◯倍 / API◯倍 / ピッチ保持再生◯倍」は診断の「Google 話速処理」に出ます。

### 言語タグは Google 側の綴りに合わせています

中国語は `cmn-CN` / `cmn-TW`、アラビア語は Chirp 3: HD が `ar-XA`、Gemini-TTS が
`ar-001` です。既定のBCP-47をそのまま送ると 400 になります。

### キーについて

- 「🔍 確認」と「🔄 声を取得」は同じ処理です。`voices.list` を読み上げ先の言語で
  引くので、**通ればその経路がまるごと生きている**ことになります。件数と、
  そのうち Chirp 3: HD が何件かを返します。
- **キーが無効なときの応答は 401 でも 403 でもなく 400**（`API_KEY_INVALID`）です。
  他の 400 と混ぜると声の名前を疑いに行かせてしまうので、メッセージを分けています。
- キーは他のTTSキーと同じ「読み上げ」区分で保存します（⚙ の記憶チェックに従います）。
  キーは <a>Google Cloud →「APIとサービス」→「認証情報」</a>で作り、同じプロジェクトで
  Cloud Text-to-Speech API を有効にしてください。キーの制限はこのAPIだけに絞るのが安全です。

## 確かめていないこと

- **実機での合成そのもの。** この作業環境に Google のキーが無いため、
  CORS（プリフライト）・エンドポイント・リクエストのスキーマ・無効キーの応答は
  実際の `texttospeech.googleapis.com` に当てて確かめましたが、
  **音が鳴るところまでは未確認**です。最初の1回は「🔍 確認」で件数が返ることを
  見てから読み上げてください。
- **`speakingRate` を Gemini-TTS が本当に拒むか。** 公式の記述があるのは Chirp 3: HD
  だけです。Gemini-TTS は話し方をプロンプトで指定する設計なので送らない方針にしましたが、
  実際に通るかは試していません（通るなら送る方が正確です）。
- **Realtime の音響が判断を変えるか。** 解析器は繋がりましたが、音響ありの `active` で
  切り方がどう変わるかは、次の記録を見るまで分かりません。
- カードをまたぐ結合、`tts-wait-end` の15秒、床の2定数、ぎざぎざの数値表現は
  従来どおり未着手です。

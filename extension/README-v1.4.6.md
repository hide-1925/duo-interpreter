# Duo Interpreter Chrome/Edge 拡張 v1.4.6

対象：`on`（TTSのみ）にしてもオリジナル音声がTeamsへ入る問題
前提：HTML v1.47.0（変更なし）

## 1. v1.4.5実環境ログで確定したこと

`duo-subtitle-interaction (17).json` と HTML診断ログ（v1.47.0）を突き合わせた。
**原因は2つあり、どちらも別々に効いている。**

### 原因A：モード切替の2回目以降が空振りしていた（`on`でも原音が入る直接原因）

セッション3で記録されたモード切替。

| 経過 | HTMLが送った切替 | アダプターが実際に差し替えたトラック |
| ---: | --- | --- |
| 1005.9s | mix | `d32d594c` へ差し替え ✅ |
| 1135.5s | off | **差し替えなし**（`d32d594c` のまま） |
| 1138.1s | **on** | **差し替えなし**（`d32d594c` のまま） |
| 1170.9s | mix | **差し替えなし** |
| 1173.2s | off | **差し替えなし** |

2回目以降は `mode-applied` だけが返り、`replaceTrack` の記録が一切ない。
senderは最初のmixトラック（原音70% + TTS100%）を持ち続けた。
**UIが`on`でも、Teamsが受け取っていたのはmixだった。**

原因は `setMode()` の構造。

```js
await Promise.all([...records.values()]
  .filter(r => r.original?.readyState==='live' && usable(r))
  .map(apply));
return mode;                 // ← 0件でも成功として返る
```

対象が0件でも `mode` を返すため、`target.js` が `mode-applied` を送り、HTML側は
`pending` を解除して新しいモードを表示する。`apply()` 自身も同じ条件で無言return
するため、**どちらも「やらなかった」ことを記録しない。**

### 原因B：接続が全体の43%しか生きていなかった

| 区間 | 長さ | 終了理由 |
| --- | ---: | --- |
| 1.8s → 91.3s | 89s | `navigation` |
| 370.8s → 481.5s | 111s | `navigation` |
| 1001.4s → 1404.9s | 404s | `transport-disconnected` |

記録1405秒のうち有効は604秒（43%）。**残り801秒は素のマイクが直接Teamsへ流れる。**
接続が無い間は拡張が何もしていない状態なので、これはTeams本来の動作である。
`navigation` は `chrome.tabs.onUpdated` の `status==='loading'` で、Teamsタブの
documentIdも実際に変わっている（`655F21EF…` → `5C693D7D…`）。Teams側のページ遷移
でセッションが落ちていた。

### 付随：復帰失敗の無限ループ

`stop()` が失敗時に `r.replacement` を残していたため、一度復帰に失敗すると以降
すべての `stop()` が同じ閉じたsenderへ再試行し続けた。ログの
`restore-failed`（`The peer connection is closed`）は**37回**、
`元マイクの復帰に失敗しました` は**34回**記録されている。

## 2. 修正

### conference-adapters/teams.js

**`setMode()` は適用できなかったモードを報告しない。**
対象が0件なら `mode` を元へ戻し、`conference-mode-skipped` 診断（要求モード・
実際のモード・record数・理由）を出したうえで例外を投げる。
UIが実態と違うモードを表示するより、失敗を見せる方が安全である。

**`apply()` は見送りを必ず記録する。** `conference-apply-skipped` に理由を出す。
判定は `blocker(r)` に集約し、`no-original-track` / `original-ended` /
`slot-no-longer-selectable` を区別する。**今回の実機で何が偽になったのかは、
アダプターが無言だったためログから特定できなかった。次回のログでは特定できる。**

**`stop()` は死んだ置換トラックを残さない。** 復帰前に `r.replacement` を落とす。
PeerConnectionが閉じている場合は会議自体が終わっており、戻すマイクが存在しない
ので復帰失敗として扱わず（`peer-closed`）、recordを破棄する。

## 3. 検証

Node VMテスト121件成功（v1.4.5は117件）。構文チェック31ファイル成功。

追加4件。うち3件はv1.4.5のソースに対して**実際に失敗することを確認済み**。

- モード切替を6回連続で行い、毎回senderのトラックが入れ替わること
- 差し替え対象が無いモード切替は、成功を返さず例外と診断を出すこと
  （v1.4.5では成功を返す＝今回の不具合）
- 閉じたPeerConnectionへの復帰は1回で終わり、以降の `stop()` で再試行しないこと
  （v1.4.5では毎回失敗を投げ続ける＝ログの37回）
- 本物の復帰失敗は従来どおり報告するが、1回のstopにつき1回だけであること

**原因Aの再現テストの限界：** 模擬環境ではrecordが健全なままのため、実機で
`filter` が0件になった条件そのものは再現できていない。追加したテストは
「0件のときに成功を返さない」という不具合の性質を固定するものである。

**未検証：** 実ブラウザーでの動作。原因Bのセッション切断は修正していない
（Teams側のページ遷移が原因で、切断時にマイクを返すのは正しい動作のため）。

## 4. 原因Bへの対処について

接続が切れること自体は仕様どおりだが、**切れたことに気づきにくい**のが問題である。
今回は8分40秒のあいだ無接続のまま会議が進んでいた。自動再接続を入れるかどうかは
挙動が大きく変わるため、今回は実装していない。診断ログで
`webConferenceMicEnabled` の false 区間を見れば、どこで切れたかは追える。

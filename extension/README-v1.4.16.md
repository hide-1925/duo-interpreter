# Duo Interpreter 拡張 v1.4.16

HTML 本体 **v1.49.5**（ビルド `20260923-v1495-route-log-dedup`）と対です。

## この版でやったこと

**診断ログが同じ1行で埋まるのを止めました。**

streaming TTS は PCM バッファごとに音声の行き先を解決します。その都度
`conference-route-rejected` と `audio-route resolve` の2行を書いていたため、
**8秒の発話ひとつで30行以上**が同じ内容で並びました。実機ログでは
**61秒・475件のうち半分近く**がこれでした。

実害は2つあります。

1. **肝心の行が埋もれる。** 判断層の往復や commit の判断理由を読むのに、
   同じ行を何十も飛ばすことになります。
2. **1時間の記録が上限に届く。** trace の上限は 40,000 行です。このペースでは
   1時間で 28,000 行前後に達し、その半分が同じ行で占められます。

行き先の判定は job と bus の状態だけで決まるので、**結果が変わったときだけ書けば
情報量は同じ**です。ルーティング自体はバッファごとに行います（実際の音声接続なので）。

`noteRoute()` は初回と、その job の行き先が変わったときだけ true を返します。
jobId の記憶は 256 件で丸ごと捨てます。捨てても余分な1行が出るだけです。

## この版で直していないこと（実機ログから分かったこと）

いただいた v1.49.2 の実機ログを読んだ結果、**体感の遅れの主因は判断層ではありません。**

|指標|実測|意味|
|---|---|---|
|STT 応答|発話終了から**約1秒**|速い。問題ではない|
|`L2CommitProxyMs`|**0.4〜11.6秒**（中央値 約6.2秒）|commit から音が鳴り始めるまでの**待ち行列**|
|`L3Ms`|4.5〜12.1秒（中央値 約9.1秒）|発話終了から読み上げ終了まで|

**待ち行列が支配項です。** 12発話・55秒のセッションで、1.8倍速に圧縮した読み上げが
合計約40秒。稼働率 73% で、しかも最初の録音が10秒上限で切れたぶん約11秒の初期遅れが
できたため、**一度も追いつきませんでした。**

加えて、**12発話のうち4つが5文字以下**（「Hm.」「そう。」「あかんな。」「อึ้ย」）で、
それぞれが Aivis の1リクエストと待ち行列の1枠を消費しています。Aivis は
**60秒あたり10リクエスト**が上限で、実測では**50秒で残り0**になりました。

**この3つはいずれも境界の判断では直りません。** 直すのは Phase 3 の床（TTS の
待ち行列を見て保持・破棄を決める層）で、そこは `floorHold()` が `null` を返す
未実装のままです。**この実機ログは、境界の精度より床のほうが効くという証拠です。**

判断層については、ログの通り **送信5 / 到達不能5 / 適用0** で、Rules が
**17回確定・訂正0件**で走り切っています（INV-08）。経路が「TypeSafe に直接」の
ままなので、**アドオン経由の経路を含む版がまだ配信されていません。**

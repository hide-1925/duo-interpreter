## この版でやったこと

**前後の空白だけの差を訂正として数えていました。**

同じログで訂正率が **0% → 13.3%（2/15）** に跳ねました。中身を見ると2件とも
**末尾に空白が1つ付いただけ**でした（38→39字、34→35字）。末尾繰越の結合で入る空白で、
読み上げも翻訳も内容は変わりません。どちらも `audioAlreadyDispatched:false` なので、
利用者に間違った音声が出たわけでもありません。

`segReviseCommittedSource` が `replacement===s.sourceText` の**完全一致**で比較していた
ためです。

**訂正率は判断層の安全性を測る基準の数字です。** INV-08 の確認も「Rules が N 回確定して
訂正0件」という形で使っています。ここが騒がしいと、**Rules と Jev の比較そのものが
濁ります。** shadow の比較に入る直前なので、先に直しました。

前後の空白だけの差なら、本文と revision は更新しますが、訂正としては数えず再翻訳も
起こしません。**黙って捨てるのではなく `commit-retouch` として記録します。**
**語の中の空白の変化は訂正のままです。**

## Jev の答えを読む（初の実データ）

### 信頼度の式が実データで厳密に一致しました

`confidence = (N × p_max − 1) / (N − 1)` を10件すべてで検算しました。

|候補数 N|p_max|計算値|報告値|
|---|---|---|---|
|2|0.74|0.48|**0.48**|
|2|0.94|0.88|**0.88**|
|3|0.53|0.295|**0.30**|
|3|0.80|0.70|**0.71**|
|4|0.42|0.227|**0.22**|
|4|0.47|0.293|**0.29**|

**N に依存することの実害も実データで出ました。**

- p_max **0.50**（N=3）→ confidence **0.24**
- p_max **0.47**（N=4）→ confidence **0.29**

**p_max では前者が上、confidence では後者が上**という逆転です。候補数は発話ごとに
2〜4と変わるので、**confidence に閾値を置くと候補の数で判定が動きます。**
仕様 §6.4 の「boundary は confidence で閾値判定しない」は、この実データで裏づけられました。
実装は選ばれた選択肢の確率（`chosenMin`）で見ています。

### Jev は Rules より「後ろで切りたい」

10件のうち **6件は Rules と一致、4件は不一致**でした。そして**不一致の4件はすべて
同じ方向**です。Jev は `C_STABLE`（確定済みの全文で切る＝より後ろ）を選び、Rules は
より手前の文境界で切っていました。

|例|Rules|Jev|Jev の確率|
|---|---|---|---|
|e4|`C_RULES_38`|`C_STABLE_39`|0.53 対 0.43|
|e5|`C_RULES_35`|`C_STABLE_90`|0.80 対 0.17|
|e7|`C_RULES_33`|`C_STABLE_60`|0.50 対 0.46|
|e9|`C_RULES_65`|`C_STABLE_100`|0.42 対 0.38|

**ばらつきではなく一貫した傾向です。** ただし確率差は e5 を除いて小さく、confidence も
0.22〜0.30 と低いままです。**どちらが良いかはこのログでは判定できません。**
訂正率と体感で比べる必要があり、それが shadow の trace を取る目的です。

### 費用は見積りよりはるかに安い

平均1,470トークン・10回で 14,700トークン。入力 \$42/Btok なので**このセッションで
\$0.0006**。この頻度（約86秒の発話で10回）を1時間に伸ばすと約420回・62万トークンで
**\$0.026（約¥4）／時間**です。

以前 ¥80〜120／時間と見積もったのは、300ms の throttle が上限まで働く前提だったためです。
**実際は確定のたびにしか投げないので、頻度は想定の20分の1でした。**

ここから先は、**この2記録が新しく暴き出した3つの穴**です。いずれも v1.49.19 の
待ちとは別の場所にあり、3つとも同じ根から出ています ――
**「答えは文の版に紐づいているのに、その版が進まなくなる場面を考えていなかった」。**

## 穴1（最も重い）— 「待て」に期限が無く、カードが停止まで放置される

記録の両方に、**112秒と83秒のあいだ確定されずに残り、最後に読み上げごと
消えたカード**があります。

```
1本目  e6  stabilityMs 112557  → audio cancelled（speech-stopped）
       e13 stabilityMs  83967  → audio cancelled（speech-stopped）
2本目  e7  s7 stabilityMs 114447 ／ e8 s8 stabilityMs 83831
```

理屈はこうです。判断層の答えは `(文, 版)` を鍵に保存します。版は**新しいテキストが
来たときだけ**進みます。認識が止まると版は止まります。そこで最後に受け取った答えが
`HOLD`（まだ切るな）だと、**その同じ答えを80ms周期で読み直し続けます。** 待つ理由は
永遠に「いま来たばかり」のままです。確定も、翻訳も、読み上げも起きません。

INV-09 は**読み上げ開始**の待ちに、INV-10 は**答えの到着**待ちに上限を置きましたが、
**返ってきた「待て」そのものには上限がありませんでした。**

### 直したこと — INV-11

⚙ → 音声 → 発話交代の判断層 → **「待て」に従う上限 ms（0＝従わない）**（既定 **2000ms**、上限10000ms）

- `HOLD`・言い直し待ち・位置確認のどれであっても、上限を過ぎたら **Rules が確定します**。
- 時計は**確定済みの部分ごと**に持ちます。話が続いて文が伸びても止まりません。
  これは意図的です。時計を「答えが無かった tick」で戻すと、Realtime のように
  200msごとに版が進む経路では上限が一度も効きません（2本目には **501文字・8部分**の
  カードがあります）。
- 打ち切った部分については、確定するまでのあいだ**静かに** Rules へ通します。
  ログは保持の開始と打ち切りの各1行だけです。
- `0` にすると「待て」を最初から採りません。`off`／`shadow` は従来どおり無関係です。

## 穴2 — 内容の同じ往復が数百回。そのまま費用です

```
1本目  送信 433 件 ／ 187秒   同じ内容（revision:1・37文字・候補3）の往復が大半
2本目  送信 1251 件 ／ 406秒  同じ内容（revision:85・78文字）の往復が大半
```

再送の抑止は「テキスト・候補・無音の長さ」が同じなら300ms止める作りでしたが、
**無音を100ms刻みで数えていました。** テキストが凍っても無音は伸び続けるので、
毎回「新しい状態」として通ってしまいます。穴1で止まったカードが、そのあいだ
ずっと聞き直していたわけです。

1リクエストおよそ1300〜1500入力トークンなので、**1回の通訳で0.6M／1.7Mトークン**
に相当します。$42/Mtok の単価では実際の金額です。

### 直したこと

⚙ → 音声 → 発話交代の判断層 → **同じ版を聞き直す上限回数**（既定 **3**、1〜20）

テキストの版が進まないなら、聞き直しても確定の判断は変わりません。回数は
**版ごと**に数えます（版が進めば新しい情報なので、予算も新しくなります）。
打ち切ったときは `turn-decision-ask-capped` を1行だけ残します。

INV-11 で「待て」に期限が付いたので、**無音が伸びたことを理由に聞き直す必要も
もう無くなりました。**

## 穴3 — 「適用」の数が意味を持っていなかった

```
1本目  送信 433  / 適用 2450
2本目  送信 1251 / 適用 3487
```

送った数より適用が多いのは、**保持している80msの tick ごとに数えていた**からです
（2450 × 80ms ≒ 196秒、記録の全長187秒とほぼ同じ ―― つまり「ほぼ常にどこかが
保持されていた」という意味でした）。

### 直したこと

- **適用は答え1件につき1回**。送信数と並べて読める数になりました。
- tick の数は失うと惜しいので **保持tick** という別の名前で出します。
- 打ち切った回数を **打切り** として状態行と診断に出します。
  ここが増えていれば、判断層が「待て」と言い続けている場面がある、という意味です。

診断の行はこうなります。

```
判断層の往復 | 送信 120 / 正常応答 118 / 解析失敗 0 / 古くて破棄 2 / 到達不能 0 / 適用 31　保持tick 240 / 打切り 3
```

## 直していないこと（記録に見えているが今回の対象外）

- **カードをまたぐ結合。** 2本目のカードは大きく（最大501文字・8部分、重なり54〜69%）、
  1本目では30秒／6秒の録音区切りが文の途中に落ちます。読み上げの束ね役が
  「カード末尾の部分＝文末」と見なすのが原因で、直すには次のSTT塊を待つ必要があります。
- **Realtime で `Prosody取得状態 Pitch=未検出`。** WebRTC 経路ではマイク波形が
  解析器に流れていません。音響特徴を渡す設定を入れても、ピッチは空のまま送られます。
  2本目の採用6件はすべて**音響なし**で出ています。
- **`tts-wait-end {"reason":"sentence-boundary","waitMs":15043}`**（2本目 e10）。
  文末を待って15秒です。床の上限とは別経路の待ちで、まだ縛っていません。
- 座席ごとのTTS経路、ぎざぎざの数値表現、床の2定数（鮮度2秒・境界0.25）は
  比較できる前後が取れるまで凍結のままです。

**境界**を固定するものです ―― 保持は最初の tick で時計を始め、上限の1ms前までは

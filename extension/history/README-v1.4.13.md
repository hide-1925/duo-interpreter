# Duo Interpreter Chrome/Edge 拡張 v1.4.13

**HTML v1.49.2 と対で動きます。**

外部レビュー（Codex）の指摘を検証し、**当たっていた4件を直した版**です。
判断層の通信はまだ成立していないため、閾値と質問文には一切触れていません。

## 1. 全体モードが上限になっていなかった（安全側の不具合）

⚙→音声の「判断モード」を `shadow` にしても、言語別を `active` にしていれば
**その言語だけ動作へ反映されていました。** 親のつまみを絞ったのに子が効き続ける形で、
「shadow なら動作は変わらない」という前提が崩れます。

全体モードを**上限**として扱い、言語別との小さいほうを採るようにしました。

| 全体 | 日本語 | 以前 | 今 |
| --- | --- | --- | --- |
| `shadow` | `active` | **active（反映される）** | `shadow` |
| `active` | `shadow` | shadow | `shadow` |
| `off` | `active` | off | `off` |

## 2. 保持していない音声を期限で捨てていた（安全側の不具合）

Floor Gate は `assist` 以上なら**保持する理由の有無に関わらず時計を回し**、
`turnFloorMaxWaitMs`（既定3秒）を超えた job に `turnFloorExpiry` を適用していました。

Phase 3 の話者フロア判定は未実装なので、**保持は一度も発生しません**。
一方で読み上げ待ちは実測で20〜40秒に達します。つまり `expiry=drop` を選ぶと、
**フロアで保持した覚えのない音声を、ただ待ち行列が長いという理由だけで捨てて**いました。

保持したときだけ時計を回すようにしました。判定そのものは `floorHold()` に切り出し、
Phase 3 までは `null` を返します。**その間 Floor Gate は無効で、読み上げ開始は
既存の overlap ルールだけで決まります。**

## 3. 疎通の成功を「HTTP 200」で判定していた

`この経路へ疎通を試す` が、200 が返っただけで「到達しました」と出していました。
**本番と同じ parse と正規化を通し、契約に載る答えが取り出せたときだけ成功**とします。
200 が返っても契約の形でなければ失敗として理由を出します。

## 4. 往復の内訳が診断に出ていなかった

送信数しか分からず、解析で落ちたのか古くて捨てたのか判別できませんでした。

```
| 判断層の往復 | 送信 12 / 正常応答 0 / 解析失敗 0 / 古くて破棄 0 / 到達不能 12 / 適用 0 |
```

## 再現できなかった指摘

「同一応答の二重カウント」は**再現できませんでした。** `committedBySource` は
commit ごと、`correctedBySource` は訂正ごとに1回だけ加算しており、応答単位では
数えていません。想定されている経路が分かれば追います。

## 5. 検査

```
NODE_PATH=$(npm root -g) node tests/run-all.cjs --with-e2e
```

INV-09 の検査は、**以前は不具合のほうを正しいとして固定していました**
（保持理由が無くても時計が回り3秒で発火する）。保持したときだけ時計が回ることと、
保持が本当に起きたときは上限が効くことの2本に分けました。
後者は Phase 3 の代役を差し込んで検証しています。

3. 「パッケージ化されていない拡張機能を読み込む」で 1 のフォルダーを指定する
4. popup の見出しが **`Chrome v1.4.13`** と出ることを確認する

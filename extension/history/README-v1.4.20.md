# Duo Interpreter 拡張 v1.4.20

HTML 本体 **v1.49.9**（ビルド `20260923-v1499-openai-tts-limits`）と対です。

## ご質問への答え — OpenAI にも上限はあります。ただし「いくら」は人によって違います

Aivis は **60秒あたり10回**という公表された固定値です。OpenAI は違います。

|項目|Aivis|OpenAI|
|---|---|---|
|上限の決まり方|公表された固定値|**アカウントの usage tier（利用実績）で変わる**|
|単位|リクエスト数／分|**リクエスト数／分と、トークン数／分の両方**|
|自分の値の調べ方|公表値を読む|**応答ヘッダを見るしかない**|

**公式の表を読んでも、あなたのアカウントの枠は分かりません。** tier は課金実績で上がって
いくので、同じ「OpenAI TTS」でも枠は人によって違います。**実際に効いている値は応答
ヘッダに入っています。**

なお `platform.openai.com` はこの作業環境から遮断されているため、**私が公式の数値表を
確認して転記することはできません。** 記憶から数字を書くと外す危険があるので書きません。
代わりに**あなたのアカウントの実値が診断に出るようにしました。**

## この版でやったこと

### 1. OpenAI 音声の実上限を記録します

応答ヘッダの `x-ratelimit-limit-requests` / `-remaining-requests` / `-reset-requests` と、
トークン側の3つ、`retry-after` を読んで記録します。

```
tts openai-ratelimit {"where":"speech-stream","requests":"498/500",
                      "resetRequests":"240ms","tokens":"199950/200000"}
```

診断の設定欄にも **「OpenAI音声の上限（直近応答）」** を追加しました。Aivis の
「課金モード（直近応答）」の隣に並ぶので、**併用したときにどちらが先に詰まるのかを
2行並べて比べられます。**

上限ヘッダが無い応答では**何も書きません。**（ログを埋めないため。前に経路判定で
やった失敗と同じ構図です。）

### 2. 429 を他の失敗と混ぜません — これが本題でした

**OpenAI 音声の経路には 429 の扱いが一切ありませんでした。**

|経路|上限に当たったとき|
|---|---|
|Aivis|60秒10回で送信を制御し、`Retry-After` を待って**2回まで再試行**|
|VOICEVOX|429 で並列数を1段下げ、`Retry-After` 中は新規要求を止める|
|**OpenAI**|**`TTS 429` として他の失敗と同じ扱い。音声を1つ捨てて終わり**|

しかも警告は `openaiTtsWarned` で**セッション中に一度しか出ません。** 会議の前半で
別の理由で1回失敗していたら、**後半で上限に当たって読み上げが飛んでも無言**でした。

429 のときは、上限に当たったことと**いつ空くか**を明示したエラーにし、通知も
30秒に1回まで出すようにしました。「なぜ読み上げが飛んだのか分からない」を無くします。

### 3. 再試行は入れていません

**意図的です。** Aivis と同じ「`Retry-After` を待って再試行」を入れるべきですが、
ストリーミング再生の途中で待って差し込む処理は、**実際の上限値と回復時間が分からない
まま設計すると、重なって鳴る・順番が入れ替わるといった別の壊れ方をします。**

まず上の記録で**あなたの枠（何回/分、何トークン/分、回復にどれだけ）**を実測し、
それを見てから再試行と Aivis との振り分けを設計します。

## 併用を考えるうえでの実測値

前版のログ（英語→日本語、翻訳あり、約50秒）では **Aivis を9回**使い、残り1/10でした。
1発話1リクエストなので、**発話が毎分10回を超えると Aivis 単独では詰まります。**

OpenAI 側の枠が分かれば、たとえば「Aivis の残りが少ないときは OpenAI へ回す」という
振り分けが設計できます。**ただし声が変わります。**同一話者の声が途中で切り替わるのを
許すかどうかは仕様の判断なので、**ご指示ください。**

## 検査


新設 `test-tts-limits`（9件）。

- ヘッダの読み取り（大小文字を区別しない、fetch と同じ挙動）
- **上限ヘッダが無い応答では何も記録しないこと**（ログを埋めない）
- 記録される数字が**公表値ではなくアカウントの実値**であること
- **429 が他の失敗と混ざらないこと**、待ち時間を `retry-after` →
  `reset-requests` → `reset-tokens` の順に拾うこと、**無いときに数字を捏造しないこと**
- 429 以外は status を保ったまま一般的な扱いになること
- 長いエラー本文が通知やログへ出る前に切られること
- **429 のときも上限値を記録すること**（なぜ起きたかが診断に残る）

# Duo Interpreter 拡張 v1.4.21

HTML 本体 **v1.49.10**（ビルド `20260923-v14910-rate-browser-voice`）と対です。

## ご指示の1つめ — 上限以降はブラウザ内蔵音声で読みます

**待たずに読みます。** これまでは API の枠が空くまで待つ設計で、実測ログでは TTS の
待ちが **20〜40秒**に達していました。声は落ちますが、間に合うほうを選びます。

|プロバイダ|上限の判定|上限中の動き（この版から）|
|---|---|---|
|Aivis|公表値（60秒10回）をこちら側で数える。**送る前に分かる**|そのままブラウザ内蔵音声で読む|
|OpenAI|usage tier 次第で**事前には分からない**|429 を受けてから一定時間、ブラウザ内蔵音声で読む|

「あと何ms 塞がっているか」を返す1つの形（`rateWait`）に揃えたので、**上限の見え方が
違うプロバイダを同じ扱いにできます。** 将来 ElevenLabs や xAI にも同じ形で足せます。

### Aivis 側で変えたこと

上限に当たったとき `segTtsWait` で待つのをやめ、**その発話をブラウザ内蔵音声で読んで
先へ進みます。** あわせて Aivis 用のまとめ処理（同一声・500文字まで1リクエストに束ねる）
は**上限中は飛ばします。** まとめるのは Aivis の枠を節約するためなので、その枠を使わない
のなら意味がありません。

```
segment tts-rate-fallback {"cardId":"e7","seq":1,"why":"aivis-window-limit",
                           "waitMs":8400,"count60s":10,"limit":10}
```

### OpenAI 側で変えたこと

**前版までは 429 のとき音声を捨てていました。** これを**ブラウザ内蔵音声で読む**ように
しました。加えて `Retry-After` / `x-ratelimit-reset-*` を読んで、**次の発話も一定時間は
OpenAI を避けます。** 1つずつ 429 を踏み直すのは無駄だからです。

読めない値（HTTP-date 形式など）のときは**控えめに60秒**待ちます。0 にすると API を
叩き続けることになります。**数字は捏造しません。**

### 音が重なる経路を1つ潰しました

OpenAI の失敗処理は `finish()` を先に呼んでいました。読み上げスロットがそこで空くので、
**ブラウザ再生を始めると次の発話と重なります。** ブラウザ再生の完了で `finish()` を呼ぶ形に
変えました（VOICEVOX のフォールバックと同じ形）。

## ご指示の2つめ — 席ごとのプロバイダは、次の版でやります

**賛成をいただいた件は、この版には入れていません。** 理由を書きます。

プロバイダの解決箇所が **34 か所**あり、設定画面は「いま選ばれている1つのプロバイダの
設定欄だけを出す」構造になっています。席ごとに別のプロバイダにすると、**Aivis の
スタイル欄と OpenAI の声欄を同時に出す**必要があり、UI の構造から手を入れます。

それ自体は難しくありませんが、**この版の変更と同時に出すと、実機で何かおかしかったとき
どちらのせいか分からなくなります。** いま毎回ログをいただいて追えているので、
**1つずつ出したほうが速く確実です。**

設計は決めてあります。

- 既存の「読み上げ」を**主プロバイダ**として残す（いまの設定はそのまま動きます）
- **「B席だけ別のプロバイダ」**を1つ追加。未設定なら主プロバイダと同じ
- 設定欄は、主と B の**両方の欄を出す**
- 上限の判定と `rateWait` は**プロバイダごと**に働くので、席を分けると枠も分かれます

**この版で上限フォールバックが意図どおり鳴るか確認できたら、次を出します。**

## 検査

```
NODE_PATH=$(npm root -g) node extension/tests/run-all.cjs --with-e2e
→ all suites pass (383 checks)
```

`test-tts-limits` を9件から17件へ。

- 上限を持たないプロバイダは**逃がさない**こと
- 残り時間がプロバイダから読まれること、枠が空いたら0に戻ること
- **負の値や壊れた値を「塞がっている」と誤解しないこと**
- OpenAI は **429 を受けるまで避けないこと**（事前に分からないので）
- **短い指示が長い待ちを打ち消さないこと**（1秒の示唆で30秒の待ちを解除しない）
- 待ち時間を `Retry-After`（秒）/ `120ms` / `1.5s` の各形式から読むこと
- **読めない値を0にせず控えめに60秒にすること**（0 は API を叩き続ける）
- 429 のとき**塞ぐのと上限値の記録が両方起きる**こと

## 変わっていないもの

- `turnDecisionMode` の既定は `off`
- Aivis の `Retry-After` 待ちと再試行は、**手動再生など待てる経路では**そのまま
- 判断層のキーは書き出しに載りません

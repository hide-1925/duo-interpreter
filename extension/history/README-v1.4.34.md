# Duo Interpreter 拡張 v1.4.34

HTML 本体 **v1.49.23**（ビルド `20260925-v14923-one-touch-latency`）と対です。

## 1. Teams で声が届かなかった件 — 止まっていたのは会議マイク送出です

`gpt-live-transcribe` の時間帯に自動で鳴った読み上げは **2件だけ**で、
その2件とも **`webConferenceMicEnabled:false`** の瞬間でした。

```
[+356.8s] audio-route resolve  route{conferenceMic:true}  webConferenceMicEnabled:false   ← e3
[+381.7s] audio-route resolve  route{conferenceMic:true}  webConferenceMicEnabled:false   ← e5
```

`gpt-4o-mini-transcribe` に切り替えたあとは4件すべて `true` で、
`conference-route-tts-only` に乗っています。**モデルの違いではなく、
その時間帯に送出が有効でなかった**というのがログの答えです。

送出の入り切りはこうなっていました（アドオンの記録から）。

|時刻|できごと|
|---|---|
|+318.9s|ボタン → **拒否**「会議送出にはAivis・OpenAI等の音声生成TTSを選んでください」|
|+343.9s|ボタン → **同じ拒否**（このとき読み上げはまだ `off`。STARTログも `"tts":"off"`）|
|+350.6s|読み上げを Aivis に変更|
|+363.7s|**有効化 成功**|
|+371.1s|**停止**（理由 `error`・本文は空）|
|+428.3s|**有効化 成功**|
|+466.8s|**停止**（`relay-timeout`）|
|+473.5s|**有効化 成功** → +491.8s にセッション停止|

**もうひとつ、カードの「先頭から再生」は会議へは流れません。**
確認のために押した2回（e4・e9）はどちらも `conference-route-rejected`
（`playbackIntent:"manual-replay"`）でした。手で鳴らした音は手元だけで鳴ります。
+441秒の再生は送出が有効な区間でしたが、それでも相手には届いていません。

`relay-timeout` は、Teamsタブ側が**12秒ごとの生存確認を更新できなかった**ときに出ます
（4秒ごとに更新する作りです）。1回目の停止は理由の本文が空で、
どちらも**なぜ更新が途切れたのかまでは今回のログから特定できません**。

## 2. gpt-live の部分結果が 7〜65秒遅れていた件は、まだ分かりません

同じログで、`gpt-live-transcribe` の部分結果の到着間隔はこうでした。

```
arrivalGapMs: 7131 / 11958 / 11787 / 42579 / 65609
```

受け取ってから画面に出るまでは 2〜13ms なので、**こちら側の処理ではありません。**
ただし **「音声がこちらから出ていたのか」を示す記録がどの経路にもありませんでした。**
Realtime翻訳の経路には送信バイト数の記録がありますが、`gpt-live-transcribe` の
経路だけ統計を取っていませんでした。

### 足したもの

`live-audio-transport` を5秒ごとに記録します。

```
live-audio-transport {"seat":"A","connection":"connected","trackState":"live",
  "trackMuted":false,"rms":0.0812,"bytesSent":148320,"packetsSent":742,"bytesSinceLast":9840}
```

`bytesSinceLast` が伸びていれば**音はこちらから出ています**（＝遅れは相手側）。
0 のままなら**出ていません**（＝こちら側の問題）。次に同じことが起きたら、
このログで切り分けられます。

## 3. 遅延 — 縮められるのは「無音待ち」だけです

`gpt-4o-mini-transcribe` の時間帯を1件ずつ測った内訳です。

|区間|実測|
|---|---|
|話し終わり → 録音を切って送る（**無音待ち**）|**0.9秒**（固定値）|
|送信 → 文字が返る（転写）|0.69 / 0.75 / 1.30 / 1.40 / **2.33** 秒|
|確定 → 読み上げの先頭が出る|0.27〜0.39秒|
|**話し終わり → 声が出るまで**|**1.95 / 1.95 / 3.6 秒**|

転写の往復は相手側の時間で、こちらからは動かせません。**動かせるのは 0.9秒だけ**でした。

### 設定にしました

⚙ → 音声 → 音声認識 → **話し終わりを待つ無音 ms**（既定 **900**、200〜2000）

- 短くすると、文の途中の息継ぎでも切れて **1回の発話が複数の認識リクエストに割れます。**
  認識の回数と料金が増え、文の切れ目も増えます。
- **自分の声をそのまま届ける用途（同じ言語・翻訳なし）では割れても実害が小さい**ので、
  300〜500ms まで下げられます。500ms にすれば 0.4秒、300ms にすれば 0.6秒 縮みます。
- `gpt-live-transcribe` はストリーミングなのでこの値を使いません。
  **本来はそちらのほうが速い経路です**（だから 2. の切り分けを先に足しました）。
- 診断とログに実際の値が出ます（`4o系の録音上限` 行、`4o-recording-cut` の
  `silenceHoldMs` と `sinceVoiceMs`）。

## 4. 「Web会議マイク音声」をワンタッチにしました

アドオンの **Web会議マイク音声** を押すと、足りない手順だけを順に実行します。

**このタブに字幕表示 → HTML本体を開く → 翻訳開始 → 会議マイクへ送出**

- すでに済んでいる手順は飛ばします。**送出中に押したときは、従来どおり送出だけを止めます**
  （手順をやり直したり、上がっているものを落としたりしません）。
- **HTML本体は前面に出しません。** ポップアップは焦点を失うと閉じるので、
  タブを前に出すと残りの手順がそこで中断されます。開いて、名乗り出るのを最大12秒待ちます。
- **途中で止まったら、どの手順で何が起きたかを出します。**
  例：`翻訳開始で止まりました：開始条件が足りません…`。
  1. の記録で最初に2回拒否された「TTSがoff」も、ここに出ます。
- **前の手順が失敗したら後ろは実行しません。** 認識が始まっていないのに
  会議マイクだけONになる状態を作らないためです。
- プリセットや入力元の構成には触れません。当て直すと利用者が選んだ構成
  （`many_to_many` など）をボタン1つで書き換えてしまうためです。

HTML本体側に `duoExtensionStart()` を足したので、**本体も一緒に更新してください。**
古い本体のままだと「HTML本体をv1.49.23以降に更新してください」と出ます。

## 確かめていないこと

- **`relay-timeout` と1回目の停止の原因。** 生存確認が途切れた理由は、今回のログでは
  特定できません。再現したら、停止の直前の `conference-bridge-state` と
  新しい `live-audio-transport` を合わせて見ます。
- **ワンタッチの実機動作。** 手順の順番・飛ばし方・止まり方は試験で固定しましたが、
  Teams の実物に対しては未確認です。特に、新しく開いた HTML 本体のタブで
  マイクの取得と AudioContext が利用者の操作なしに始まるか（許可済みオリジンなので
  始まるはずですが）は実機で見てください。
- **無音待ちを下げたときの割れ方。** 300〜500ms を実際の会議で試した結果はありません。
- Google TTS の合成、カードをまたぐ結合、`tts-wait-end` の15秒は従来どおり未着手です。

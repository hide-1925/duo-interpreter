# Duo Interpreter 拡張 v1.4.2 — Teams加工済み送信音声への対応

HTML本体はv1.47.0のままで使えます。拡張だけを更新してください。

## 差し替え

1. このZIPを解凍し、中身を現在のDuo拡張フォルダーに上書きします。manifest.jsonが同じ階層になるようにしてください。
2. Chromeの拡張機能管理画面でDuoを再読み込みし、版が1.4.2であることを確認します。
3. TeamsとDuo本体のタブを再読み込みし、会議に入り直します。ページ側にも変更があるため、拡張だけの再読み込みでは切り替わりません。
4. 通常どおり開始し、「web会議マイク音声」をONにします。

## 今回のログで確定した停止理由

v1.4.1の導入は正常です。マイク取得成功1件、接続済み会議通信1件、有効な音声送信1本が存在する一方、アドオンの判定は `unproven-web-audio` で対象0件となっていました。
Teamsが送信している加工済み音声の上流を追跡しきれず、アドオン自身が接続を拒否しています。加工内部の具体的な方式は、このログからは確定できません。
HTMLのテキスト入力由来のTTSは `local-text` / `automatic` として会議送出対象に判定され、生成・再生も成功しています。しかし `webConferenceMicEnabled:false` のため送出されていません。

## 修正した接続判定

マイク由来を追跡できる通常の音声は、従来どおり選択します。追跡できない加工音声には、次の条件をすべて満たす場合だけ、ユーザーが接続ボタンを押した時点で送信先を特定する補助判定を使います。

- 有効な音声送信が会議フレーム内で1本だけ。
- その送信元の会議通信がconnectedである。
- その音声がWeb Audioの出力として観測されている。
- 生存しているマイクの取得元が1つだけ。複製は同じ取得元として数える。
- 観測された画面共有トラックが存在しない。生存している複製も数える。
- 加工グラフに、由来不明の別ストリーム、メディア要素、既知の音源等を混ぜている証拠がない。

この補助判定は送信先の一意性を利用した推定です。マイク由来の完全な証明とは区別し、診断に `selectionMethod: unique-processed-sender` と記録します。複数候補・画面共有中・複数マイク取得元の場合は推測で置き換えません。
ミュート維持、音声モード切替、解除時の元のTeams送信音声への復帰を維持しています。

## 瞬間的なノイズについて

今回のTTS接続失敗は上記の判定によるもので、ノイズによる故障と示す証拠はありません。
タブ音声の取得に伴う再生経路の切替がノイズの原因である可能性に対し、タブ音声のローカル再生開始を0から50ミリ秒でフェードインする変更を加えました。認識用の入力音声にはこの音量変更を適用しません。
実際のノイズの原因や解消は未確認です。オーディオ機器側の切替に起因する場合、この変更だけでは解消しないことがあります。
